magi/a3a6/A の magi.toml をそのまま main に置いた結果

レビュー済みの内容（magi/a3a6/A:magi.toml）は 差分なしでリポジトリルートに配置済み。verify.gate は .github/workflows/ci.yml の check ジョブと 一致（install → lint → build → test）、merge.base はこのリポジトリの 実際のデフォルトブランチ main と一致、 magi doctor と gate の手動実行はどちらも通った。

ただし [merge] mode = "none" がそのまま入っている

[merge]
mode = "none"   # ← このリポジトリの magi.toml が明示的に上書き
base = "main"

このブランチが今日まで放置されていた理由そのものが、当時の mode = "none"（手動マージ案内を出すだけで、誰も実行しない） だった。machine 層 (~/.config/magi/config.toml) は すでに mode = "pr" に切り替え済みで、その変更のコメントは まさに「"none" は直ったはずのものが直らないまま止まる」という同じ理由を 挙げている。

# machine layer (~/.config/magi/config.toml) の該当コメント
[merge]
base = "main"
mode = "pr"
# "none" はブランチを残して手でマージするコマンドを表示するだけで、
# その「手で」を誰もやらないと直ったはずのものが直っていないまま止まる。
# run 20260907-075524-520f がまさにそれで…

レイヤーの優先順位は repo の magi.toml が machine を上書きする （Config の解決順: built-in → machine → .magi/config.toml → magi.toml）。このファイルを machine の変更後にタイムスタンプで 確認すると、run 20260908-082051-a3a6 が動いた時点ではまだ machine 側も "none" だった（machine config の更新はその約24分後）。つまりこの mode = "none" は「このリポジトリだから手動マージにしたい」という 意図的な判断ではなく、当時の既定値をそのまま書き出しただけの可能性が高い。

選択肢結果
そのまま mode = "none" で置く レビュー済みの内容を一切変えない。ただし今後このリポジトリで magi run/magi review が勝っても、machine の "pr" は上書きされ続け、毎回また「勝ったのに誰も マージしない」が起きうる。
mode 行を削除する [merge] base = "main" だけ残し、mode は machine 層の "pr" を継承させる。今後は自動で PR が立ち、 land_approval 経由で承認待ちになる（サイレントに放置されない）。 レビュー済み内容から1行減る変更になる。
